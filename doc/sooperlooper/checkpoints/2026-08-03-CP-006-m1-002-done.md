# Checkpoint: M1-002 receiver lifecycle and strict parser completed

## Objective
Implement the production SooperLooper OSC receiver (M1-002) with liblo server
thread lifecycle, strict path/signature allow-list, typed inbound events,
thread-safe dispatch, bounded queue with overflow counting, and deterministic
shutdown.

## Completed
- `sooperlooper_receiver` pimpl class with liblo server thread lifecycle.
- Catch-all trampoline routes all incoming OSC through the event queue; no user
  code runs on the liblo thread.
- Strict `(path, types)` allow-list enforces only supported OSC type tags
  (i f d h c s S); unknown tags are rejected at handler registration time.
- `handle()` registers typed callbacks; `dispatch()` drains the queue and invokes
  them from the calling thread (safe, non-realtime context).
- `poll_event()` non-blocking and `wait_event()` blocking receive paths.
- Bounded queue (`max_queue_size`, default 4096); overflow increments an atomic
  `dropped_count` (monotonic, `memory_order_relaxed` load).
- `start()` is idempotent (returns true if already running); `stop()` is
  idempotent (no-op if already stopped).
- Start/stop concurrency contract documented: not thread-safe for concurrent
  calls from different threads; external serialization required if needed.
- `m_dropped_count` is `std::atomic<unsigned long long>`, avoiding the race
  between the mutex-protected increment and the unsynchronized diagnostic read.
- Comprehensive test suite (`sooperlooper_receiver_test.cpp`):
  - lifecycle (start, stop, restart),
  - handler registration and dispatch,
  - duplicate registration rejection,
  - type-tagged send/receive (string, int),
  - poll_event with unhandled path,
  - wait_event blocking receive,
  - bounded queue overflow and dropped_count,
  - concurrent handler registration and dispatch.
- CI integration: `.github/workflows/audio-core.yml` compiles and runs the
  receiver test on every PR touching audio code.

## Risks and unresolved questions
- The receiver does not yet track engine generation; a future task (M1-004)
  will add generation-scoped stale-feedback rejection.
- `start()/stop()` are not safe for concurrent calls from different threads;
  this is acceptable because the receiver is designed for single-thread control
  (audio/UI thread). If multi-thread control is needed in the future, the caller
  must provide external synchronization.
- liblo error handler currently silences errors; a production-grade error
  reporting path is a future concern.
